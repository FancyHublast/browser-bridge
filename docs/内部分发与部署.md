# 内部分发与部署指南

> 目标：让**业务同事尽量少操作**就能用上 browser-bridge。
> 配套文件：`server/deploy/`（部署脚本、systemd、nginx、Windows 策略模板）

---

## 0. 先分清你要的是哪一种（这一步选错，后面全白做）

浏览器自动化有一条**物理约束**：**浏览器必须在"操作实际发生"的那台机器上运行**。
把服务放到服务器上，并不会让浏览器搬到服务器上——**服务只是个指令中转站**。

所以先回答：**谁在点"开始"？**

| 场景 | 谁触发 | 浏览器在哪 | 推荐架构 | 用户要装什么 |
|---|---|---|---|---|
| **A. 同事自己在 AI 里说话** | 人 | 同事电脑 | 本机服务 + 扩展 | 扩展 + 一个 exe |
| **B. 定时自动跑（每天取数）** | 定时器 | **某台常开的机器** | 服务在服务器，浏览器在常开机 | 扩展（只在那台机器） |
| **C. 同事点一个按钮完成固定任务** | 人 | 同事电脑 | **纯扩展，不要服务** | 只装扩展 |

**关键判断**：

- 如果你的目的是"让业务同事自己能取数"→ 走 **C**（最简，零服务）。扩展里直接写死流程，点一下就跑。
- 如果目的是"每天早上自动把各店铺数据拉到服务器"→ 走 **B**。但注意：**那台机器的浏览器必须一直开着、且保持登录**，这是最容易翻车的地方。
- **A 是当前架构的原生形态**。每个用户在自己电脑上跑一个常驻服务，扩展连它 ——
  这条路**不需要 token、不需要填地址**，是给同事装的最省事形态，详见 [第 2 节](#2-本机常驻服务一键安装--开机自启)。

> ⚠️ 场景 B 有个坑：Chrome 长期无人值守运行会被系统休眠、被"内存节省"回收标签页、
> 登录态过期。真要这么做，得配：关睡眠、关标签页丢弃、加登录态巡检。

## 1. 安装简化的三个层次

| 层次 | 用户要做的操作 | 适合谁 | 靠什么实现 |
|---|---|---|---|
| **L0**（现状） | 装 Python → 建 venv → 装依赖 → 配 MCP → 加载扩展 → 手填地址和 token | 只有你自己 | 手动 |
| **L1** | 双击一次 exe（装成开机自启）+ 装扩展 | 技术同事 | PyInstaller 打包 + 扩展手动加载 |
| **L2** | **什么都不做** | 业务同事 ✅ | 扩展策略静默安装 + token 策略下发 |

**L2 的全部秘密就是 Chrome 企业策略**：一套策略同时解决"装扩展"和"配 token"两件事，
用户在浏览器里点都点不到（策略下发的扩展用户无法删除）。

## 2. 本机常驻服务：一键安装 + 开机自启

**先说结论：服务在本机跑的时候，token 这件事直接消失了。**

服务监听 `127.0.0.1` 时按设计**不需要 token**（`bridge.py` 的规则是"监听非回环地址才强制要 token"），
而扩展的默认地址就是 `ws://127.0.0.1:8765`。于是：

- 不用填服务地址
- 不用填 token
- 不用分发任何密钥

**同事装完扩展就能连上。** 这不是少了一步，是把整个"密钥分发"问题删掉了 ——
这也是"本地起服务"相对"服务上服务器"最大的优势。

### 2.1 一个必须澄清的限制

**扩展无法安装本地程序。** 扩展跑在浏览器沙箱里，没有执行本地命令的权限，
所以"装完插件就自动把服务装好"**在技术上做不到**
（除非先单独装一个 native messaging host，而那本身又要一次安装）。

能做到的是：**把"一次手动"压缩成双击一个文件，之后全部自动。**

### 2.2 一键安装脚本

| 文件 | 作用 |
|---|---|
| `server/install-local-service.bat` | 双击一次：检查 Python → 建 venv 装依赖 → 注册登录自启 → 启动并自检 |
| `server/uninstall-local-service.bat` | 完整卸载：停服务 + 删自启项（**只终止带 `--ws-only` 的进程**，不会误伤 agent 拉起的实例） |

自启优先用**计划任务**（登录后延迟 20 秒启动，避开开机高峰），
被域策略禁用时自动退回**注册表 Run 键**，效果等价。
两者都指向 `pythonw.exe` —— GUI 子系统程序，**不会弹黑窗口**。

### 2.3 ⚠️ 最容易踩的坑：和 agent 抢端口

`mcp_server.py` 是**一个进程同时提供 WebSocket 服务和 MCP 服务**。这意味着：

> **同一台机器上，agent（WorkBuddy / Claude Code）和自启服务会抢同一个 8765 端口。**
> 先起的赢，后起的直接退出（`exit(2)`），而症状是"浏览器能力莫名其妙没了"。

所以按机器用途分开：

| 这台机器拿来干嘛 | 要不要装自启服务 |
|---|---|
| 你用 agent 做自动化 | **不要装** —— agent 的 MCP 客户端会自己拉起服务 |
| 同事只装扩展、不用 agent | **装** —— 这正是自启服务的目标场景 |
| 两者都要 | 见 2.4 |

安装脚本第 3 步会**检测端口占用者并认得出是谁**（看命令行里有没有 `--ws-only`），
遇到 agent 拉起的实例会明确劝你选 N。
（`--ws-only` 就是脚本用来区分"自启服务"与"agent 拉起的服务"的标志。）

### 2.4 一个服务，多个 agent 会话（以及和自启服务共存）

**最常被问到的问题**：为什么在第二个会话里 `browser_*` 工具显示不可用，但插件明明显示"已连接"？

**原因**：`~/.workbuddy/mcp.json` 是**全局**配置，所有会话共用同一份。
而它是 `command + args`（stdio 模式），意味着 **每个会话都会拉起自己的 `mcp_server.py` 进程**，
每个进程都要绑 `127.0.0.1:8765`。而一个端口只能有一个进程：

```
会话 A 启动 → 绑定 8765 成功 → 工具可用，扩展连它
会话 B 启动 → 端口被占 → BridgeError("端口已被占用") → sys.exit(2) → 该会话工具全不可用
```

所以你看到的"连接正常"和"另一个会话不可用"并不矛盾——扩展连的是会话 A 的那个进程。

**解法：改用 HTTP 模式，一个常驻实例供所有会话共享。**

```bash
# ① 启动一个常驻实例：同时提供 WS（给扩展）+ HTTP（给所有会话）
server/start-http-server.bat
# 等价于：python server/mcp_server.py --http
```

```json
// ② 把 ~/.workbuddy/mcp.json 里的 browser-bridge 改成 HTTP 形式
"browser-bridge": {
  "type": "streamableHttp",
  "url": "http://127.0.0.1:8766/mcp",
  "timeout": 60000
}
```

改完重启 agent。之后所有会话都连这一个实例，**不再抢端口**。

> **`--http` 曾经有个坑，v1.3.4 已修**：mcp 2.x 的 `MCPServer` 没有 `settings` 属性，
> 端口只能通过 `run(**kwargs)` 传给 `run_streamable_http_async()`。旧代码用
> `try: mcp.settings.port = ... except: pass` 设置端口，异常被静默吞掉 ——
> 配置写 `8766`，服务却监听在 SDK 默认的 **8000**，日志里还打印 8766，极难排查。
> 现在按 SDK 大版本分支处理。如果你看到日志说 8766 但 `netstat` 里没有，
> 就是这个老 bug。

**这个模式的两个代价，先想清楚**：

1. **必须有常驻进程**。它一停，所有会话一起没工具（stdio 模式下至少"当前会话"是自足的）。
   所以配合 2.2 的自启脚本用，把启动参数换成 `--http`。
2. **多会话共用一个浏览器**，会**互相干扰**：A 会话点了按钮，B 会话看到的页面也变了；
   A 会话在导航，B 会话的定位就会失效。这是"共享同一个浏览器"的固有问题，不是 bug。
   真要并行操作不同页面，就别共享——用不同端口各起一个实例 + 各自连不同的浏览器 profile。

> ⚠️ `--http` 暴露出去的**就是浏览器控制权**。只绑 `127.0.0.1` 时风险可控（本机程序可连）；
> 一旦要跨机器访问，必须叠加认证（mTLS / Basic Auth / IP 白名单）。

### 2.5 同事机器不想装 Python 怎么办

三条路，按推荐度排：

1. **打包成单个 exe（推荐）**：用 PyInstaller 把 `mcp_server.py --ws-only` 打成无依赖 exe，
   同事双击一次即可，完全不需要 Python。自启逻辑不变，只把脚本里的 `PYW`/`SRV` 换成 exe 路径。
   ⚠️ exe 要过公司杀软，先给 IT 报备，否则可能被静默隔离。
2. **便携式 Python**：随包带一个 embeddable Python + 依赖，脚本指向它。
3. 找 IT 走软件分发流程。

## 3. Token 分发：四种方式对比（本节是重点）

| 方式 | 用户操作 | 安全性 | 适用 |
|---|---|---|---|
| 手填（现状） | 复制粘贴 | 差 —— token 会随着截图/聊天记录外传 | 自己用 |
| 发文档/截图让同事照抄 | 照着敲 | 差 —— 同上，且必然有人填错 | 3~5 人小团队 |
| **Chrome 企业策略（managed storage）** | **零操作** | **好 —— 用户改不了，也不经手** | **公司批量 ✅** |
| 一次性配对码换 token | 输 6 位码 | 中 | 没有域控的环境 |

### 3.1 企业策略怎么做（本项目已原生支持）

扩展侧已经实现：**`chrome.storage.managed` 优先于本地手填配置**，
且被策略锁定时面板里的输入框自动只读、保存按钮变成"由企业策略锁定"——
同事不会因为"改了没生效"来问你。

**扩展 ID 已固定为：`ejajjndahiklljjjpnmefhmbinaegkdc`**

> 为什么必须先固定 ID：从源码目录加载的扩展，ID 是按**路径**算出来的。
> 同事把文件夹放在桌面还是 D 盘，ID 都不一样，策略就没法精确指定这条扩展。
> 现在 `manifest.json` 里加了 `key` 字段，任何机器上 ID 都相同。

#### 方式一：注册表下发（单机 / 用脚本批量）

`server/deploy/extension-policy.reg` 就是模板，改两处即可：

```reg
Windows Registry Editor Version 5.00

[HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Google\Chrome\3rdparty\extensions\ejajjndahiklljjjpnmefhmbinaegkdc\policy]
"wsUrl"="wss://bridge.yourcompany.com"
"wsToken"="换成32位以上随机串"

; 同时静默安装扩展（写的是扩展 ID + 你自己的 update_url）
[HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Google\Chrome\ExtensionInstallForcelist]
"1"="ejajjndahiklljjjpnmefhmbinaegkdc;https://bridge.yourcompany.com/updates/browser-bridge.xml"
```

#### 方式二：组策略（域环境批量，推荐）

Chrome 的 ADMX 模板 → **计算机配置 → 管理模板 → Google Chrome → 扩展**：

- `配置扩展的强制安装列表` → 填 `扩展ID;update_url`
- `通过扩展策略配置扩展`（或 `3rdparty` 策略）→ 填
  `{"ejajjndahiklljjjpnmefhmbinaegkdc":{"wsUrl":"wss://...","wsToken":"..."}}`

#### 方式三：验证是否下发成功

在同事的 Chrome 地址栏输入：

```
chrome://policy
```

能看到 `ExtensionSettings` / `3rdparty` 里出现本扩展的 ID，且顶部没有红色报错 → 成功。
再打开扩展面板，地址框应该是灰的、按钮显示"由企业策略锁定"。

## 4. 服务部署到服务器

### 4.1 ⚠️ 必须先理解：服务端是**单客户端**设计

`server/bridge.py` 里 `self._ws` 是**单个槽位**，新连接会顶掉旧连接：

```python
# 只保留一条连接：新连接顶掉旧的，避免指令发给了错误的浏览器
if old is not None and old is not websocket:
    log.info("新连接顶替旧连接")
    await old.close(code=4002, reason="superseded by new connection")
```

这是**刻意的**，不是没写完。原因：MCP 工具（`browser_click(...)`）里**没有"发给谁"这个参数**。
如果一个服务端接多个用户的浏览器，agent 说"点一下登录"，服务端不知道该发给谁——
**改错方向就是 A 用户的操作作用在 B 用户的浏览器上**，这比重连失败危险得多。

**推论：一个服务端实例 = 服务一个用户。多用户 = 多实例。** 见 4.4 的多实例配置。

### 4.2 ⚠️ 必须上 TLS（否则扩展连不上）

扩展的 service worker 连 `wss://` 时**会正常校验证书**，自签证书会被直接拒绝。
两条可行路线：

| 路线 | 做法 | 适合 |
|---|---|---|
| **内网 CA** | 用公司 CA 签发服务器证书，并把 CA 根证书推到所有客户端的"受信任的根证书颁发机构" | 有域控 |
| **公网域名 + Let's Encrypt** | 给 `bridge.yourcompany.com` 签免费证书（DNS 验证即可） | 最省事 ✅ |

> 内网直连 `ws://192.168.x.x:8765` 在多数情况下能用（扩展 SW 不像网页那样受混合内容限制），
> 但**明文传输 token 与所有页面内容**，公司网络里等于裸奔。别省这一步。

### 4.3 部署步骤（Debian/Ubuntu，可复制）

```bash
# ① 拉代码（服务器也要配 SSH over 443，公司网络封 22 端口）
git clone git@github.com:FancyHublast/browser-bridge.git /opt/browser-bridge
cd /opt/browser-bridge

# ② 建虚拟环境（3.10+）
python3 -m venv server/.venv
server/.venv/bin/pip install -i https://pypi.org/simple/ -r server/requirements.txt

# ③ 生成 token（每个用户一个，别共用）
python3 -c "import secrets; print(secrets.token_urlsafe(32))"

# ④ 写配置。注意 host 用 127.0.0.1 —— 由 nginx 在前面挡着，
#    服务本身不要直接暴露到公网
cat > server/config.json <<'EOF'
{
  "host": "127.0.0.1",
  "port": 8765,
  "token": "把上一步生成的串填这里",
  "heartbeat_seconds": 20,
  "call_timeout_seconds": 60,
  "max_message_mb": 64,
  "screenshot_dir": "/var/lib/browser-bridge/shots",
  "log_level": "INFO",
  "http_host": "127.0.0.1",
  "http_port": 8766
}
EOF

# ⑤ 先手动跑一次，确认没有权限/依赖问题
server/.venv/bin/python server/mcp_server.py --ws-only
# 看到「WebSocket 服务已监听 ws://127.0.0.1:8765（鉴权：token）」即正常，Ctrl+C 退出

# ⑥ 交给 systemd 托管（见 4.4），不要用 nohup
```

### 4.4 systemd：多实例（每个用户一套）

`server/deploy/browser-bridge@.service` 是模板服务，`@` 后面是用户名：

```bash
sudo cp server/deploy/browser-bridge@.service /etc/systemd/system/

# 为 zhangsan / lisi 各起一个实例（端口 8765 / 8766）
sudo mkdir -p /etc/browser-bridge
sudo cp server/config.json /etc/browser-bridge/zhangsan.json   # 改 port 与 token
sudo sed -i 's/"port": 8765/"port": 8766/' /etc/browser-bridge/lisi.json

sudo systemctl daemon-reload
sudo systemctl enable --now browser-bridge@zhangsan browser-bridge@lisi
sudo systemctl status browser-bridge@zhangsan
sudo journalctl -u browser-bridge@zhangsan -f
```

### 4.5 nginx：wss 反代（按路径分流到各实例）

见 `server/deploy/nginx-snippet.conf`。核心是把 `/u/zhangsan` 转到本机 8765、
`/u/lisi` 转到 8766：

```nginx
map $http_upgrade $connection_upgrade { default upgrade; '' close; }

location /u/zhangsan {
    proxy_pass http://127.0.0.1:8765;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_read_timeout 3600s;   # WebSocket 长连接，别用默认 60s
}
```

配置好后，同事扩展里填：

```
wss://bridge.yourcompany.com/u/zhangsan/?token=xxxxxxxx
```

### 4.6 ⚠️ MCP 的 HTTP 端点也要保护

`mcp_server.py --http` 会把 MCP 以 Streamable HTTP 暴露出去（给远程 agent 用）。
**这个端点没有额外鉴权的话，内网里谁扫到端口谁就能控制浏览器。**

- 只在需要远程 agent 时开 `--http`
- 一定要放在 nginx 后面再加上一层认证（mTLS / Basic Auth / 内网 IP 白名单）
- 只给单个用户用时，干脆别开 —— 让 agent 跑在本机、走 stdio

### 4.7 防火墙

```bash
# 只放 nginx，服务本身绑 127.0.0.1 就已经出不去
sudo ufw allow 443/tcp
sudo ufw deny 8765/tcp
```

## 5. 扩展的批量安装（私有分发）

Chrome 应用商店**上架不了**这类扩展（政策禁止"绕过登录限制"，且 `debugger`+`allows all sites` 权限过重）。
企业内部分发的标准做法是自己托管更新清单：

```bash
# ① 打 crx 包（用生成扩展 ID 时的那把私钥，务必保管好）
"/c/Program Files/Google/Chrome/Application/chrome.exe" \
  --pack-extension="X:\path\to\browser-bridge\extension" \
  --pack-extension-key="X:\path\to\browser-bridge-extension-key.pem"
# 产出 extension.crx

# ② 放到 web 服务器
#    /var/www/updates/browser-bridge.crx
#    /var/www/updates/browser-bridge.xml   （模板见 server/deploy/extension-update.xml）
```

`update_url` 指向那个 xml，再用 3.1 的 `ExtensionInstallForcelist` 策略下发，同事的 Chrome
会自动安装并在每次打开时检查更新——**全程无需用户操作**。

> 更新 XML 与 crx 放在**内网**即可，不必暴露公网。

> ⚠️ **这套强制安装只适合"真·企业分发"场景**（域控 + 内网 HTTPS 更新源 +
> HKLM 写入权限 + 机器上没有别的强制安装策略）。个人单机 / 无管理员权限的机器
> **不要硬套**：实测在 HKLM 已被其它扩展的 `ExtensionInstallForcelist` 占用的机器上，
> 写进 HKCU 的策略会被压制，Chrome 一直显示"正在更新"，最终把扩展判为策略禁用
> （`disable_reasons:[256]`，开关灰色打不开）；更新源若指向 `127.0.0.1` 的本地服务，
> 服务一停扩展同样失效。**这种场景直接用"加载已解压"即可** —— 只要扩展目录放在
> 固定路径（不要放带时间戳的临时会话目录），重启和升级 Chrome 都不会掉，
> 不依赖策略、不依赖更新服务、不需要管理员权限。

## 6. 业务同事的最终体验（L2 完成态）

```
IT 一次性操作                    同事侧体验
─────────────────────────────    ──────────────────────────
① 部署服务 + 生成每人 token        （无）
② 下发 Chrome 策略（装扩展+配token） 打开 Chrome → 扩展已在，显示"已连接"
③ 给同事一个快捷方式               点一下 → 完成
```

同事**不需要**：装 Python、跑脚本、打开黑窗口、填地址、复制 token、改任何设置。

## 7. 风险与注意事项（别跳过）

| 项 | 说明 |
|---|---|
| **服务器形态的权限风险** | 服务端能向任意连上来的浏览器下发指令。谁能访问这个端口，谁就能控制别人的浏览器。务必 TLS + 独立 token + 端口不对外 + 审计日志 |
| **token 是唯一凭据** | 泄漏一个 token = 那台浏览器被接管。按人分发、可单独吊销、定期轮换 |
| **浏览器必须开着** | 场景 B 里，目标机器关机/休眠/退出登录 = 任务失败。要加巡检与告警 |
| **扩展权限很重** | `cookies` + `debugger` + `<all_urls>`。公司内分发应由 IT 评估后走策略下发，不要私下流传 crx |
| **合规** | 只用于操作**本单位拥有并有权操作**的账号。不要用它绕过第三方平台的安全机制 |
| **私钥保管** | `browser-bridge-extension-key.pem` 是推送扩展更新的唯一凭据。丢了只能换 key（扩展 ID 会变，所有客户端要重装） |

## 附：最省事的组合（如果只想要一个答案）

**场景 C + L2**：

1. 把同事要用的那个固定流程直接写进扩展（不依赖 Python 服务）
2. 用企业策略静默装上
3. 同事点一下扩展图标 → 事情办完

代价是失去 agent 的灵活性（流程写死），换来的是**零服务、零 token、零运维**。
如果同事的需求是"每天就是导那几张表"，这条路综合成本最低。
